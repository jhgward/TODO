## Clarifications

### Session 2026-09-30

- Q: 순서 변경 요청의 `position`은 무엇인가? → A: 대상 칼럼 내 **인덱스**(0부터, 이동 티켓을 제외한 목록 기준).
  실제 순서 값은 서버가 계산한다.
- Q: 이미 Done인 티켓을 다시 완료 처리하면? → A: 변경 없이 현재 티켓을 그대로 반환한다(성공).
- Q: Backlog로 이동할 때 시작일은? → A: 어느 칼럼에서 오든 Backlog로 이동하면 시작일을 비운다.
  다른 칼럼에서 TODO로 들어오면 시작일을 현재 시각으로 설정한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 칸반 보드 현황 조회 (Priority: P1)

사용자는 보드를 열어 전체 할 일을 4개 칼럼(Backlog, TODO, In Progress, Done)별로 순서대로 본다.
마감이 지난 미완료 티켓은 오버듀로 표시되고, 완료한 지 24시간이 지난 티켓은 Done 칼럼에서 사라진다.

**Why this priority**: 보드 조회 없이는 생성한 티켓을 볼 수 없고, 이동·완료·수정의 결과도 확인할 수 없다.

**Independent Test**: 여러 상태의 티켓을 준비한 뒤 보드를 조회해 칼럼별 그룹화, 순서, 오버듀 표시, Done 24시간
필터, 전체 개수를 확인한다.

**Acceptance Scenarios**:

1. **Given** 티켓이 하나도 없을 때, **When** 보드를 조회하면, **Then** 4개 칼럼이 모두 빈 목록이고 전체 개수는 0이다. (TC 002-1)
2. **Given** 여러 상태의 티켓, **When** 보드를 조회하면, **Then** 각 티켓이 자기 상태의 칼럼에만 나타난다. (TC 002-2)
3. **Given** 한 칼럼에 여러 티켓, **When** 보드를 조회하면, **Then** 순서 값 오름차순으로 정렬된다. (TC 002-3)
4. **Given** 표시되는 티켓이 N개, **When** 보드를 조회하면, **Then** 전체 개수는 N이다(숨겨진 Done 티켓 제외). (TC 002-4)
5. **Given** 23시간 전에 완료한 티켓과 25시간 전에 완료한 티켓, **When** 보드를 조회하면, **Then** 앞의 것만
   Done 칼럼에 나타난다. (TC 002-5, 002-6)
6. **Given** 어떤 티켓이든, **When** 보드를 조회하면, **Then** 각 티켓에 오버듀 여부와 네 가지 날짜 항목(시작예정일,
   종료예정일, 시작일, 종료일)이 포함된다. (TC 002-7, 002-8)
7. **Given** 종료예정일이 어제인 미완료 티켓, **When** 조회하면, **Then** 오버듀이다. Done이거나, 종료예정일이
   없거나, 오늘·미래이면 오버듀가 아니다. (TC 008-1 ~ 008-7)

### User Story 2 - 티켓 상세 조회 (Priority: P2)

사용자는 카드를 눌러 티켓 한 건의 전체 정보를 본다.

**Why this priority**: 수정·삭제·완료의 진입점이며, 다른 기능의 결과 확인에도 쓰인다.

**Independent Test**: 생성한 티켓을 식별자로 조회해 모든 항목과 오버듀 여부가 오는지, 없는 식별자와 잘못된 형식이
각각 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 존재하는 티켓, **When** 상세 조회하면, **Then** 모든 항목과 오버듀 여부가 반환된다. (TC 003-1, 003-4)
2. **Given** 존재하지 않는 식별자, **When** 조회하면, **Then** "티켓을 찾을 수 없습니다"로 안내된다. (TC 003-2)
3. **Given** 숫자가 아닌 식별자 `abc`, **When** 조회하면, **Then** 검증 실패로 거부되고
   "요청 형식이 올바르지 않습니다"가 안내된다. (TC 003-3)

### User Story 3 - 티켓 내용 수정 (Priority: P2)

사용자는 티켓의 제목, 설명, 우선순위, 시작예정일, 종료예정일 중 원하는 항목만 고친다. 설명과 날짜는 비울 수 있다.

**Why this priority**: 등록 후 내용이 바뀌는 일이 흔하지만, 조회(P1) 없이는 의미가 없다.

**Independent Test**: 티켓을 만들고 항목을 하나씩 수정해 해당 항목만 바뀌고 나머지는 유지되는지, 상태 같은 시스템
항목은 바뀌지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 티켓, **When** 제목만 수정하면, **Then** 제목만 바뀌고 나머지는 유지된다. (TC 004-1)
2. **Given** 티켓, **When** 우선순위를 LOW로 수정하면, **Then** 우선순위가 바뀐다. (TC 004-2)
3. **Given** 설명·종료예정일·시작예정일이 있는 티켓, **When** 각각 빈 값(null)으로 수정하면, **Then** 해당
   항목이 비워진다. (TC 004-3, 004-4, 004-6)
4. **Given** 티켓, **When** 시작예정일을 수정하면, **Then** 반영된다. (TC 004-5)
5. **Given** 존재하지 않는 식별자, **When** 수정하면, **Then** "티켓을 찾을 수 없습니다"로 안내된다. (TC 004-7)
6. **Given** 티켓, **When** 아무 항목이나 수정하면, **Then** 수정 시각이 갱신된다. (TC 004-8)
7. **Given** 티켓, **When** 상태를 Done으로 바꾸려는 값을 함께 보내면, **Then** 무시되고 상태는 그대로다. (TC 004-9)
8. **Given** 티켓, **When** 201자 제목·1001자 설명·잘못된 우선순위·오늘 또는 과거 종료예정일로 수정하면,
   **Then** 생성과 같은 메시지로 거부된다.

### User Story 4 - 티켓 완료 처리 (Priority: P2)

사용자는 할 일을 끝내면 Done으로 옮긴다. 시스템이 종료일을 기록하고 Done 칼럼 맨 위에 놓는다.

**Why this priority**: 완료는 칸반의 핵심 흐름이고 종료일·24시간 표시 규칙의 출발점이다.

**Independent Test**: 티켓을 완료 처리해 상태·종료일·순서·수정 시각을 확인하고, 없는 식별자가 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 미완료 티켓, **When** 완료 처리하면, **Then** 상태가 Done이 되고 종료일이 현재 시각(±수 초)으로
   설정된다. (TC 005-1, 005-2)
2. **Given** Done 칼럼에 다른 티켓이 있을 때, **When** 완료 처리하면, **Then** 새로 완료한 티켓이 Done 맨 위에
   온다. (TC 005-3)
3. **Given** 존재하지 않는 식별자, **When** 완료 처리하면, **Then** "티켓을 찾을 수 없습니다"로 안내된다. (TC 005-4)
4. **Given** 미완료 티켓, **When** 완료 처리하면, **Then** 수정 시각이 갱신된다. (TC 005-5)
5. **Given** 이미 Done인 티켓, **When** 다시 완료 처리하면, **Then** 아무것도 바뀌지 않고 현재 티켓이 반환된다.

### User Story 5 - 드래그앤드롭으로 상태·순서 변경 (Priority: P2)

사용자는 카드를 끌어 다른 칼럼으로 옮기거나 같은 칼럼 안에서 순서를 바꾼다(Done으로의 이동 제외).
시스템이 시작일·종료일을 규칙에 따라 관리하고, 필요하면 칼럼 전체 순서를 다시 매긴다.

**Why this priority**: 칸반의 주된 조작이지만 조회(P1)와 완료(US4)가 있어야 전체 흐름이 검증된다.

**Independent Test**: 티켓을 칼럼 사이·칼럼 안에서 옮겨 상태, 순서, 시작일·종료일 변화를 확인하고, Done을 대상으로
하거나 잘못된 상태·없는 티켓이 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Backlog 티켓, **When** TODO의 첫 자리로 옮기면, **Then** 상태가 TODO가 되고 TODO 맨 위에 온다. (TC 007-1)
2. **Given** 같은 칼럼의 티켓들, **When** 한 티켓을 다른 자리로 옮기면, **Then** 상태는 그대로이고 순서만 바뀐다. (TC 007-2)
3. **Given** Backlog 티켓, **When** TODO로 옮기면, **Then** 시작일이 현재 시각으로 설정된다. (TC 007-3)
4. **Given** TODO 티켓, **When** Backlog로 옮기면, **Then** 시작일이 비워진다. (TC 007-4)
5. **Given** Done 티켓, **When** TODO로 옮기면, **Then** 종료일이 비워지고 시작일이 설정된다. (TC 007-5)
6. **Given** Done 티켓, **When** Backlog로 옮기면, **Then** 종료일과 시작일이 모두 비워진다. (TC 007-6)
7. **Given** TODO 티켓, **When** In Progress로 옮기면, **Then** 시작일은 그대로다. (TC 007-7)
8. **Given** 인접한 두 티켓의 순서 값 사이에 빈 정수가 없을 때, **When** 그 사이에 끼워 넣으면, **Then** 칼럼
   전체가 1024 간격으로 다시 매겨지고, 순서 값이 바뀐 다른 티켓들이 함께 반환된다. (TC 007-8)
9. **Given** 대상 상태로 Done을 보내면, **Then** 검증 실패로 거부된다. 그 밖의 잘못된 상태 값은
   "상태는 BACKLOG, TODO, IN_PROGRESS 중 선택해주세요"로 거부된다. (TC 007-9, 007-10)
10. **Given** 존재하지 않는 티켓, **When** 옮기면, **Then** "티켓을 찾을 수 없습니다"로 안내된다. (TC 007-11)
11. **Given** 티켓, **When** 옮기면, **Then** 수정 시각이 갱신된다. (TC 007-12)

### User Story 6 - 티켓 삭제 (Priority: P3)

사용자는 필요 없어진 티켓을 영구 삭제한다.

**Why this priority**: 보드를 정리하는 부가 기능이며 다른 기능이 의존하지 않는다.

**Independent Test**: 티켓을 삭제한 뒤 다시 조회하면 찾을 수 없고, 없는 식별자 삭제는 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 존재하는 티켓, **When** 삭제하면, **Then** 본문 없는 성공 응답이 오고 재조회 시 찾을 수 없다. (TC 006-1)
2. **Given** 존재하지 않는 식별자, **When** 삭제하면, **Then** "티켓을 찾을 수 없습니다"로 안내된다. (TC 006-2)

### Edge Cases

- 식별자가 숫자가 아니거나 0 이하이면 모든 식별자 기반 요청이 "요청 형식이 올바르지 않습니다"로 거부된다.
- 순서 변경의 인덱스가 칼럼 길이보다 크면 맨 뒤에, 0이면 맨 앞에 놓는다. 음수·소수는 형식 오류로 거부한다.
- 비어 있는 칼럼으로 옮기면 순서 값은 0이다.
- 두 티켓 사이에 넣을 때 중간값은 내림한 정수다. 두 값 사이에 넣을 정수가 없으면(간격 ≤ 1) 칼럼 전체를 다시 매긴다.
- 같은 칼럼·같은 자리로 옮겨도 성공하며 상태·시작일·종료일은 바뀌지 않는다.
- 같은 칼럼 안에서 순서만 바꿀 때는 시작일을 바꾸지 않는다(TODO 안에서의 재정렬 포함).
- In Progress에서 TODO로 되돌리면 시작일이 현재 시각으로 다시 설정된다.
- 수정 요청에 바꿀 항목이 하나도 없으면(빈 요청) 아무것도 바꾸지 않고 현재 티켓을 반환한다.
- 수정으로 제목을 빈 값·공백만으로 바꾸려 하면 "제목을 입력해주세요"로 거부한다.
- 종료예정일이 **오늘**인 미완료 티켓은 오버듀가 아니다. "오늘"은 Asia/Seoul 기준이다.
- 종료일이 정확히 24시간 전인 Done 티켓은 아직 보드에 표시된다(24시간 "이내").
- Done 티켓은 종료예정일이 지났어도 오버듀가 아니다.

## Requirements *(mandatory)*

### Functional Requirements

**보드 조회 (FR-002, FR-008)**

- **FR-001**: 시스템은 모든 티켓을 Backlog, TODO, In Progress, Done 네 칼럼으로 묶어 MUST 반환하며, 티켓이 없는
  칼럼도 빈 목록으로 포함한다.
- **FR-002**: 각 칼럼의 티켓은 순서 값 오름차순으로 MUST 정렬된다.
- **FR-003**: Done 칼럼에는 종료일이 현재로부터 24시간 이내인 티켓만 MUST 포함된다.
- **FR-004**: 응답에는 표시되는 티켓의 전체 개수가 MUST 포함된다.
- **FR-005**: 조회되는 각 티켓에는 오버듀 여부가 MUST 포함된다. 오버듀는 "종료예정일이 Asia/Seoul 기준 오늘보다
  이전이고 상태가 Done이 아님"이며 저장하지 않고 조회 시 계산한다.

**상세 조회 (FR-003)**

- **FR-006**: 사용자는 식별자로 티켓 한 건의 모든 항목과 오버듀 여부를 조회할 수 MUST 있다.
- **FR-007**: 존재하지 않는 식별자에 대한 조회·수정·완료·삭제·이동은 "티켓을 찾을 수 없습니다"로 MUST 거부된다.
- **FR-008**: 양의 정수가 아닌 식별자는 "요청 형식이 올바르지 않습니다"로 MUST 거부된다.

**수정 (FR-004)**

- **FR-009**: 사용자는 제목, 설명, 우선순위, 시작예정일, 종료예정일 중 보낸 항목만 수정할 수 MUST 있고, 보내지
  않은 항목은 유지된다.
- **FR-010**: 설명, 시작예정일, 종료예정일은 빈 값(null)을 보내 비울 수 MUST 있다.
- **FR-011**: 수정 값의 제약과 거부 메시지는 생성과 MUST 같다: 제목은 앞뒤 공백 제외 1~200자, 설명 최대 1000자,
  우선순위 LOW·MEDIUM·HIGH, 날짜는 YYYY-MM-DD, 종료예정일은 Asia/Seoul 기준 내일 이후.
- **FR-012**: 상태, 순서, 시작일, 종료일은 수정 요청으로 MUST NOT 바뀐다(보내도 무시).
- **FR-013**: 수정·완료·이동이 실제로 티켓을 바꾸면 수정 시각이 MUST 갱신된다.

**완료 (FR-005)**

- **FR-014**: 완료 처리 시 시스템은 상태를 Done으로, 종료일을 현재 시각으로 MUST 설정하고, 티켓을 Done 칼럼 맨
  위(Done 최솟값 − 1024, Done이 비어 있으면 0)에 놓는다.
- **FR-015**: 이미 Done인 티켓의 완료 처리는 아무것도 바꾸지 않고 현재 티켓을 MUST 반환한다.

**삭제 (FR-006)**

- **FR-016**: 사용자는 티켓을 영구 삭제할 수 MUST 있고, 성공 시 본문 없는 응답을 받는다.

**상태·순서 변경 (FR-007)**

- **FR-017**: 사용자는 티켓을 Backlog, TODO, In Progress 중 한 칼럼의 지정한 자리(0부터의 인덱스)로 옮길 수 MUST
  있다. Done을 대상으로 한 요청은 검증 실패로 거부되고, 그 외 잘못된 상태 값은
  "상태는 BACKLOG, TODO, IN_PROGRESS 중 선택해주세요"로 거부된다.
- **FR-018**: 시스템은 자리에 맞는 순서 값을 MUST 계산한다: 맨 앞은 첫 티켓 − 1024, 맨 뒤는 마지막 티켓 + 1024,
  사이는 앞뒤 값의 중간(내림), 빈 칼럼은 0.
- **FR-019**: 앞뒤 값 사이에 넣을 정수가 없으면 시스템은 대상 칼럼 전체를 1024 간격(0부터)으로 MUST 다시 매기고,
  순서 값이 바뀐 다른 티켓들의 식별자와 새 순서 값을 함께 반환한다. 다시 매기지 않았으면 그 목록은 비어 있다.
- **FR-020**: 다른 칼럼에서 TODO로 옮기면 시작일을 현재 시각으로, 다른 칼럼에서 Backlog로 옮기면 시작일을 빈 값으로
  MUST 설정한다. 그 외 이동은 시작일을 바꾸지 않는다.
- **FR-021**: Done에서 다른 칼럼으로 옮기면 종료일을 MUST 비운다.
- **FR-022**: 이동에 따른 모든 변경(이동 티켓 + 다시 매긴 티켓들)은 전부 적용되거나 전부 적용되지 않아야 MUST 한다.

**공통**

- **FR-023**: 모든 실패는 오류 코드와 한국어 안내 메시지 하나를 일관된 형식으로 MUST 반환하며, 본문 해석 불가·
  자료형 불일치는 "요청 형식이 올바르지 않습니다"로 거부한다.
