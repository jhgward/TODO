## Clarifications

### Session 2026-09-30

- Q: Backlog가 비어 있을 때 첫 티켓의 순서 값은? → A: 0. API_SPEC.md 응답 예시(−1024)는 첫 티켓
  이후 "칼럼 내 최솟값 − 1024"가 적용된 경우를 뜻하며, 명세 문서 수정은 필요 없다.
- Q: 종료예정일이 오늘이면 허용하는가? → A: 거부한다. 종료예정일은 내일(Asia/Seoul)부터 허용한다.
- Q: 형식이 잘못된 요청(본문 해석 불가, 자료형 불일치, 날짜 형식 오류)의 안내 메시지는? → A: 공통 메시지
  하나 — "요청 형식이 올바르지 않습니다".

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 제목만으로 빠르게 할 일 등록 (Priority: P1)

사용자는 떠오른 할 일을 제목만 입력해 즉시 등록한다. 등록된 티켓은 Backlog 칼럼 맨 위에 나타나고,
입력하지 않은 항목에는 기본값이 적용된다. 제목이 비어 있거나 너무 길면 등록이 거부되고 이유를 안내받는다.

**Why this priority**: 할 일 등록은 칸반 보드의 모든 기능(조회, 이동, 완료)의 출발점이다. 제목만으로
등록되는 것만으로도 "잊기 전에 기록한다"는 핵심 가치를 제공한다.

**Independent Test**: 제목만 담아 티켓을 생성하고, 반환된 티켓이 Backlog 상태·중간 우선순위이며 기존
Backlog 티켓들보다 앞에 배치되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Backlog가 어떤 상태이든, **When** 제목 "테스트 할일"만 입력해 생성하면, **Then** 티켓이
   생성되고 상태는 Backlog, 우선순위는 MEDIUM, 설명·시작예정일·종료예정일은 비어 있다. (TC 001-1)
2. **Given** 티켓을 하나 생성한 직후, **When** 티켓을 하나 더 생성하면, **Then** 나중에 만든 티켓이
   Backlog에서 더 앞(위)에 배치된다. (TC 001-10)
3. **Given** 정상 입력, **When** 티켓을 생성하면, **Then** 시작일과 종료일(시스템 기록 항목)은 비어
   있고 생성·수정 시각이 기록된다. (TC 001-11)
4. **Given** 제목 없이, **When** 생성을 요청하면, **Then** 거부되고 "제목을 입력해주세요"가 안내된다. (TC 001-3)
5. **Given** 빈 문자열 또는 공백만 있는 제목, **When** 생성을 요청하면, **Then** 거부되고
   "제목을 입력해주세요"가 안내된다. (TC 001-4, 001-5)
6. **Given** 201자 제목, **When** 생성을 요청하면, **Then** 거부되고
   "제목은 200자 이내로 입력해주세요"가 안내된다. (TC 001-6)

---

### User Story 2 - 상세 정보를 포함해 등록 (Priority: P2)

사용자는 등록 시 설명, 우선순위, 시작예정일, 종료예정일을 선택적으로 함께 입력해 할 일의 중요도와
기한을 관리한다. 허용 범위를 벗어난 값은 거부되고 이유를 안내받는다.

**Why this priority**: 우선순위와 기한은 오버듀 판정·뱃지 표시 등 후속 기능의 입력이지만, 제목만으로
등록되는 P1 없이는 의미가 없다.

**Independent Test**: 모든 항목을 채워 생성한 뒤 입력값이 그대로 반영되었는지, 범위를 벗어난 각 항목이
해당 메시지로 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 제목·설명·우선순위 HIGH·미래의 시작예정일·미래의 종료예정일, **When** 생성하면,
   **Then** 모든 입력값이 반영된 티켓이 Backlog에 생성된다. (TC 001-2)
2. **Given** 1001자 설명, **When** 생성을 요청하면, **Then** 거부되고
   "설명은 1000자 이내로 입력해주세요"가 안내된다. (TC 001-7)
3. **Given** 우선순위 "URGENT", **When** 생성을 요청하면, **Then** 거부되고
   "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요"가 안내된다. (TC 001-8)
4. **Given** 종료예정일 2020-01-01, **When** 생성을 요청하면, **Then** 거부되고
   "종료예정일은 오늘 이후 날짜를 선택해주세요"가 안내된다. (TC 001-9)

### User Story 3 - 형식이 잘못된 요청 처리 (Priority: P3)

요청 자체를 해석할 수 없거나(본문 형식 오류), 항목의 자료형·날짜 형식이 맞지 않는 경우에도 시스템은
내부 오류를 드러내지 않고 일관된 형식의 검증 실패로 응답한다.

**Why this priority**: 정상 사용 흐름(P1, P2)에서는 발생하지 않지만, 클라이언트 오류나 비정상 요청에서
시스템이 예측 가능하게 동작해야 한다 (constitution 원칙 III, IV).

**Independent Test**: 해석 불가능한 본문, 숫자 제목, 잘못된 날짜 형식을 각각 보내 모두 검증 실패로
거부되고 기술적 오류 원문이 노출되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 해석할 수 없는 요청 본문, **When** 생성을 요청하면, **Then** 서버 오류가 아닌 검증 실패로
   거부되고 "요청 형식이 올바르지 않습니다"가 안내된다.
2. **Given** 제목이 문자열이 아닌 값(예: 숫자), **When** 생성을 요청하면, **Then** 검증 실패로 거부되고
   "요청 형식이 올바르지 않습니다"가 안내된다 (기술적 기본 메시지 노출 금지).
3. **Given** `2026/10/01`처럼 YYYY-MM-DD가 아닌 날짜, **When** 생성을 요청하면, **Then** 검증 실패로 거부되고
   "요청 형식이 올바르지 않습니다"가 안내된다.

---

### Edge Cases

- 제목이 정확히 200자이면 허용되고, 201자부터 거부된다. 앞뒤 공백은 길이 판단에서 제외한다.
- 설명이 정확히 1000자이면 허용된다.
- 종료예정일이 **오늘**이면 거부되고, **내일**이면 허용된다.
- "오늘"은 Asia/Seoul 기준이다. 한국 시간 자정 전후에도 판정이 한국 날짜를 따른다.
- 여러 항목이 동시에 잘못된 경우 한 가지 메시지만 안내한다 (제목 → 설명 → 우선순위 → 시작예정일 →
  종료예정일 순으로 첫 번째 오류).
- 사용자가 상태·순서·시작일·종료일을 직접 지정해 보내도 무시되고 규칙에 따른 값이 적용된다.
- 시작예정일이 종료예정일보다 늦거나 과거여도 거부하지 않는다 (명세에 제약 없음).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 사용자는 제목을 필수로, 설명·우선순위·시작예정일·종료예정일을 선택적으로 입력해 새 티켓을
  생성할 수 MUST 있다.
- **FR-002**: 시스템은 제목을 앞뒤 공백을 제외하고 1~200자로 MUST 제한한다. 누락·빈 값·공백만 입력 시
  "제목을 입력해주세요", 200자 초과 시 "제목은 200자 이내로 입력해주세요"로 거부한다.
- **FR-003**: 시스템은 설명을 최대 1000자로 MUST 제한하고, 초과 시 "설명은 1000자 이내로 입력해주세요"로
  거부한다. 미입력 시 설명은 비어 있다.
- **FR-004**: 시스템은 우선순위를 LOW, MEDIUM, HIGH 중 하나로 MUST 제한하고, 미입력 시 MEDIUM을 적용하며,
  그 외 값은 "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요"로 거부한다.
- **FR-005**: 시작예정일과 종료예정일은 YYYY-MM-DD 형식의 날짜 MUST 이며, 미입력 시 비어 있다.
- **FR-006**: 시스템은 Asia/Seoul 기준 오늘 또는 그 이전인 종료예정일을 "종료예정일은 오늘 이후 날짜를
  선택해주세요"로 MUST 거부한다 (내일부터 허용).
- **FR-007**: 새 티켓의 상태는 입력과 무관하게 항상 Backlog MUST 이다.
- **FR-008**: 새 티켓은 Backlog 맨 위에 MUST 배치된다. 순서 값은 기존 Backlog 티켓 중 최솟값 − 1024이며,
  Backlog가 비어 있으면 0이다.
- **FR-009**: 새 티켓의 시작일·종료일(시스템 기록 항목)은 비어 있고, 생성·수정 시각은 자동으로 MUST 기록된다.
- **FR-010**: 생성에 성공하면 시스템은 생성된 티켓의 모든 항목(식별자, 제목, 설명, 상태, 우선순위, 순서,
  시작예정일, 종료예정일, 시작일, 종료일, 생성·수정 시각)을 MUST 반환한다.
- **FR-011**: 검증에 실패하면 시스템은 티켓을 생성하지 않고, 오류 코드(검증 실패)와 한국어 안내 메시지
  하나를 일관된 형식으로 MUST 반환한다.
- **FR-012**: 요청 본문 해석 불가, 자료형 불일치, 날짜 형식 오류도 서버 오류가 아닌 검증 실패로 MUST
  처리하며, "요청 형식이 올바르지 않습니다"로 안내하고 기술적 오류 원문을 노출하지 않는다.
- **FR-013**: 사용자가 보낸 상태·순서·시작일·종료일 값은 MUST 무시된다.

### Key Entities

- **Ticket(티켓)**: 칸반 보드의 할 일 한 건. 사용자 입력 항목(제목, 설명, 우선순위, 시작예정일,
  종료예정일), 시스템 관리 항목(상태, 칼럼 내 순서, 시작일, 종료일, 생성·수정 시각), 고유 식별자를 가진다.
  생성 시점에는 항상 Backlog 칼럼에 속한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 제목만 입력해 10초 이내에 할 일을 등록할 수 있다.
- **SC-002**: TC-API-001의 11개 인수 시나리오와 User Story 3의 형식 오류 시나리오가 100% 명세된 결과를 낸다.
- **SC-003**: 잘못된 입력의 100%가 명세된 한국어 안내 메시지로 거부되며, 내부 오류 원문이 사용자에게
  노출되는 경우는 0건이다.
- **SC-004**: 연속으로 생성한 티켓은 100% 가장 최근 것이 Backlog 맨 위에 표시된다.
- **SC-005**: 등록 결과는 사용자가 체감하기에 즉시(1초 이내) 확인된다.

## Assumptions

- 단일 사용자 MVP로 인증·권한 구분이 없다 (PRD).
- 날짜 판정의 "오늘"은 Asia/Seoul 기준이다 (API_SPEC 공통 규칙).
- 제목은 앞뒤 공백을 제거한 값으로 저장한다 (공백만 입력 거부 규칙과 일관성).
- 여러 검증 오류가 동시에 발생하면 입력 항목 순서상 첫 번째 오류 메시지만 반환한다 (응답 형식이 메시지 1개).
- 명세에 없는 입력 항목은 무시한다.
- 이 명세의 범위는 티켓 생성 기능 자체이며, 생성 폼 UI(TC-COMP-004)와 우선순위 뱃지 색상은 범위 밖이다.
- 기존 테스트·구현은 TC 001-1, 2, 3, 6, 8, 9만 다룬다. 001-4, 5, 7, 10, 11과 User Story 3은 테스트가
  없으며, 이 중 001-11(시작일·종료일 비어 있음)만 현재 동작상 우연히 충족된다.
